# 项目清理与优化检查

本次范围：移除旧版本兼容逻辑、清空服务端开发数据；保留本地个人数据、公共示例资源和 Git 历史。

## 已落实

| 原问题 | 当前处理 |
| --- | --- |
| 新旧菜单 API 回退导致重复请求，404 含义混淆 | 客户端只读取 `/catalog`，删除旧菜单和图片清单 GET 接口 |
| 旧个人图片迁移、永久图片读取和释放入口 | 删除客户端迁移、服务端旧路由及旧上传目录 |
| 旧餐厅分类补值、无分类活动放开全部餐厅 | 分类与活动餐厅集合必填，旧格式不自动修复 |
| `Buffet`、`UseCase.Token` 两套装配和注入命名 | 统一 `Bootstrap` 与 `InjectionToken` |
| 本地保存仍经过原件工作流和无用的部分同步包装 | 直接调用本地保存用例，删除待同步查询及手动重试链路 |
| 每个 HTTP 请求执行一次全库回收事务 | 定时批量清理；访问目标房间时只检查该房间，确实过期才删除 |
| 房间回收手动逐表删除，事件追加逐条写入 | 使用外键级联删除、`createMany` 批量追加；保持 CAS 与完整批次事务原子性 |
| 多轮增量迁移及旧时间戳修复脚本 | 合并为当前结构的单一基线，旧开发库重建 |
| 心跳与提交标识可缺省 | 当前订阅要求心跳与菜单信封；远程批次要求提交标识 |

心跳、断线补齐、重复批次忽略、触摸与鼠标事件去重、文件系统路径适配属于当前功能，没有作为旧版本兼容删除。未进行性能基准测试，不宣称具体提速比例。

## 后续值得优化

1. **本地持久化的变更跟踪。** `ManifestStorage` 和 runtime 每次发布仍扫描完整状态并比较 JSON。历史记录、房间日志增加后，加菜成本会随全部本地数据增长。可由事务明确记录修改键，保存不可变投影并按键失效，保留当前原子发布和故障恢复能力。
2. **服务端事件的重复存储。** `RoomBatch.document` 和 `RoomEvent.document` 都保留完整事件 JSON。目前查询主要按完整批次读取。应先明确单事件索引的实际用途，再决定只保留索引字段，避免两份 payload 长期占用空间。
3. **房间传输访问凭证。** 当前 CAS 约束版本，不验证提交者身份。若服务开放到公网，可以增加房间级读写凭证及消息速率限制；服务端仍保持纯事件中继，不承担领域业务运算。
4. **图片元数据索引。** 房间图片目前以数组保存，商品逐个查找。大菜单可在收到信封时建立餐厅/商品二级 Map，让每张卡片的查找成本固定。

这些后续项应分别实施并保留故障、并发与断线回放测试，避免一次性改写已经明确的多人事务协议。

## 服务端重置方式

停止服务端后，在根目录执行 `npm run db:reset`，再执行 `npm run server`。基线为 `20261102000300_baseline`；房间、房间码、事件、私人菜单和临时图片一并清空，公共图片资源保留。本地缓存中的旧房间不再存在，需要创建新房间。
